# 提案:时间线账本与公司供数架构(Schema v6 / Ingest v2)

日期:2026-07-07
状态:已与所有者对齐九项关键决策,进入分步实施
关联文档:[`docs/temporal-facts-v1.md`](temporal-facts-v1.md)、live 库 `schema.md`(v5)

---

## 1. 背景与目标

本库有两个并行目标:

1. **个人外挂大脑**:通过摄入沉淀出带时间线的知识库,每个时间点保留"当时的事实 + 当时的思考和理解",复盘时可回放。
2. **公司供数**:作为公司多 agent 投研产品的检索补充知识库,以版本化快照形式同步到公司环境,公司自建检索。

当前系统的结构性缺口:

- **事实有时间线,理解没有时间线。** Temporal Facts(v1)记录了"世界发生了什么"并有 supersedes/证伪链;但"当时怎么理解"只存在于页面正文,`## 当前理解(随时更新)` 每次摄入被 merge 覆盖,旧理解不可检索、不可回放。
- **摄入太慢、太贵。** 单篇约 1 小时:完整源文(90k 字符)被重发给每个页面写手(15-20 次),update 页每次重新生成整页几百行输出。
- **落页不准。** 词法候选检索 + 一次全局 plan call 分配 15+ 页面,错配漏配是结构性的。
- **Markdown 无控制增长。** 概念页 188/1143 页超 500 行;`## 验证记录`/`## 历史案例` 等手写时间线章节是主要膨胀点;2000 行软上限仅 warning,plan budget 默认不生效。
- **没有供数出口。** 无 visibility 分级、无导出管道、无数据契约。

## 2. 已锁定的九项决策(2026-07-07 采访)

| # | 问题 | 决策 | 架构后果 |
|---|---|---|---|
| 1 | 公司产品接入方式 | **同步快照到公司环境** | 做版本化快照发布管道,不做实时服务;工作区与消费隔离 |
| 2 | 共享边界 | **过滤个人层** | `visibility` 字段第一天进 schema(页面 frontmatter + 账本记录) |
| 3 | 检索归属 | **公司自建检索** | 交付物是数据契约(Markdown + JSONL + manifest),不交付检索服务 |
| 4 | raw/ 出境 | **全部出去** | 溯源链天然完整;快照带 evidenceLevel 元数据供公司侧门控群聊舆情 |
| 5 | LLM 执行层 | **只用 codex 登录态** | 提速靠减少调用次数 + 缩小 prompt(claim 一次抽取 + 章节补丁小输出),目标 15-20 分钟/篇 |
| 6 | 公司产出回流 | **人工筛选后回流** | 保持单写入者;约定 `raw/公司研究/` + `sourceKind: agent_research`,摄入默认降权 |
| 7 | 判断账本归属 | **判断也给公司** | judgments.jsonl 进出口契约;仅仓位/盈亏等个人执行数据留个人层 |
| 8 | claim 路由实现 | **embedding 走 API** | 路由 = 实体码精确匹配(第一优先)+ embedding 相似度 + 歧义批量 codex 裁决 |
| 9 | 页面人工编辑 / 总结页出境 | **基本只读;章节级过滤** | 页面可演进为"账本渲染视图";出口过滤做到章节粒度 |

**中枢抽象:章节化页面模型。** 决策 9 的章节级出口过滤和摄入侧的章节锚定补丁共用同一个页面解析器(frontmatter + `##` 章节树,无损往返)。它是本提案所有组件的地基,最先实现。

## 3. 目标架构

### 3.1 三账本 + 渲染视图

```
data/facts/temporal_edges.jsonl   # 事实账本:世界发生了什么(已有,v1)
data/facts/judgments.jsonl        # 判断账本:我当时怎么理解(新增)
wiki/**/*.md                      # 知识页:最新状态 + 自动时间线区块(渲染视图)
raw/**                            # 不可变原始证据(不变)
```

**判断账本记录(judgment-v1)**:

```json
{
  "id": "jg_<确定性hash>",
  "subject": "AI服务器电源",
  "entityKey": "entity:ai服务器电源",
  "kind": "thesis",
  "claim": "当前是订单兑现期而非叙事扩散期,主线从整机切向上游电源",
  "basedOnFacts": ["tf_xxx", "tf_yyy"],
  "confidence": "中",
  "validAt": "2026-06-12",
  "status": "held",
  "supersedes": [],
  "verifyBy": "2026-07-15",
  "verifyNote": "看Q2订单是否转收入",
  "visibility": "team",
  "sourcePath": "raw/日复盘/2026-06-12-复盘.md",
  "sourceHash": "..."
}
```

- `kind`:`thesis`(判断)/ `expectation`(预期)/ `lesson`(教训)/ `stance`(仓位观点,默认 `visibility: personal`)。
- `status`:`held` / `revised` / `invalidated` / `expired`。修正时新增记录并 `supersedes` 旧 id,不改旧行(与 facts 同规则)。
- 复用 facts 的全部机制:确定性 id 去重、manifest 独立 `judgmentWrites` 区域、apply dry-run 展示、索引重建。
- 防膨胀:`verifyBy` 过期 60 天未复核的判断在 Lint 中自动标 `expired` 候选(人工确认)。

### 3.2 章节化页面模型(中枢)

- 页面 = frontmatter + preamble + `##` 章节树;解析/序列化无损往返。
- **章节锚定补丁**:摄入的页面写手输出操作列表而非整页:
  `replace_section` / `append_to_section` / `insert_section_after` / `update_frontmatter`。
  程序化 merger 应用补丁并校验(锚必须存在、不允许删除未触及章节——防缩水校验下放到章节粒度)。
- **自动渲染区块**:`<!-- AUTO:<name>:START -->` … `<!-- AUTO:<name>:END -->`(复用分时主线索引的注入模式)。`## 时间线`、概念页 `## 验证记录`、模式页 `## 历史案例` 改为自动区块,由程序从 facts+judgments 按 `entity_key` 渲染最近 N 条 + 完整时间线链接。LLM 不再手写这些章节。
- **章节可见性**:章节体首行可放 `<!-- visibility: personal -->`;未标记的章节继承页面 frontmatter 的 `visibility`(默认 `team`)。
- **周期性整固**:页面累积 K 次补丁(默认 5)或超行数阈值后,Lint 时触发一次整页重写(dry-run → 人审 → write),把碎片消化、过期内容降权、事实类内容迁出到账本。

### 3.3 Frontmatter 新增字段(schema v6)

```yaml
entity_key: entity:ai服务器电源   # 可选;股票页已有 code:,概念/模式页补此字段
visibility: team                  # 可选;team(默认)/ personal
```

两个字段均可选,存量页面不需要迁移;校验只对显式提供且值非法的情况给 warning(不 fatal)。

### 3.4 摄入 v2:claim 为中心

```
Phase 1  抽取(唯一读全文处;分片并发,codex 调用 ≈ 分片数)
  → 结构化 claims:{ 实体, 断言, 类型(事实型/解释型), 证据等级, 时间锚, 原文行号 }
Phase 2  路由(几乎零 LLM)
  实体码精确匹配 → embedding 相似度(API) → 歧义批量一次 codex 裁决
  事实型 → factWrites;解释型 → judgmentWrites;C/D 弱证据 → 仅 source archive
Phase 3  页面章节补丁(codex 调用 ≈ 命中页数,但输入 ~8k 字符、输出仅补丁)
Phase 4  程序化 housekeeping + 自动区块渲染 + apply(沿用现有安全壳)
```

预期:codex 调用次数从 ~20 次大 prompt 大输出降为"分片数 + 1 次裁决 + 命中页数"次小 prompt 小输出;单篇 1 小时 → 15-20 分钟;落页准度由逐条 claim 路由 + 实体键保证,且每条 claim 带原文行号可回溯、可做 routing eval。

### 3.5 快照导出管道(供数)

```
apply --write 成功
  → export snapshot(默认每日收盘后一次 + 可手动触发)
      1. 页级过滤:frontmatter visibility: personal 的页面整页排除
      2. 章节级过滤:personal 章节裁剪(总结页的个人交易复盘章节等)
      3. 账本过滤:judgments/facts 中 visibility: personal 的记录排除(stance 默认排除)
      4. raw/ 全量同步(决策 4)
      5. 产出 snapshot-manifest.json:版本号(内容 hash)、生成时间、
         计数、schema 版本、数据契约版本
  → 推送到公司环境(复用 sag-sync / 双机同步的既有通道)
```

**数据契约(company-snapshot-contract-v1)**,公司自建检索的消费面:

| 内容 | 格式 | 关键字段 |
|---|---|---|
| 知识页 | Markdown + frontmatter | `entity_key`、`type`、`updated`、章节结构稳定可 chunk |
| 事实账本 | temporal_edges.jsonl | `id`、`entityKey`、`predicate`、`status`、`evidenceLevel`、`validAt`、`sourcePath` |
| 判断账本 | judgments.jsonl | `id`、`entityKey`、`kind`、`status`、`validAt`、`basedOnFacts`、`supersedes` |
| 原始证据 | raw/** 全量 | 与 `sourcePath` 溯源链接 |
| 快照清单 | snapshot-manifest.json | 版本号进公司侧引用,可精确追溯"当时读的是哪一版" |

**回流约定(决策 6)**:公司 agent 产出经人工筛选后放入 `raw/公司研究/YYYY-MM-DD-<主题>.md`,摄入时 `sourceKind: agent_research`,证据等级默认 ≤ B,并在 claim 抽取中标注机器来源防循环引用。

### 3.6 as-of 回放

`ask --as-of YYYY-MM-DD`:以该日期为界重建当时视图——facts/judgments 只取 `validAt ≤ 日期` 且在该日期尚未被 supersede/invalidate 的记录为主证据。用途:复盘"当时为什么这么想"、训练飞轮的 as-of 截断样本(判断账本直接产出"给定当时事实→当时判断→后来验证结果"三元组)。

## 4. Schema v6 变更清单(live 库 `schema.md`,由所有者确认后应用)

1. 新增「判断账本」章节:`data/facts/judgments.jsonl` 定义、`judgmentWrites` 写入边界、kind/status 词表、防膨胀规则。
2. Frontmatter 规范加入可选 `entity_key`、`visibility` 字段。
3. 概念页 `## 验证记录`、模式页 `## 历史案例`、概念/股票页 `## 时间线` 标注为程序化自动区块,LLM 不手写。
4. 股票页 `## 当前理解(随时更新)` 语义改为"最新判断摘要;历史判断入账本"。
5. Query 章节加入 `--as-of` 语义说明。
6. Lint 新增「判断复核」步骤:到期 `verifyBy` 的判断强制标 held/revised/invalidated;revised/invalidated 事件自动产出《交易进化史》草稿条目。
7. 「去重与页面职责边界」权威位置表加一行:判断/预期/修正链 → `data/facts/judgments.jsonl`。
8. `wiki/查询/think-*.md` 类思考产物迁往 `.llm-wiki/`;高价值的带 `entity_key` 归档。
9. 数据流全貌图补充:快照导出管道、`raw/公司研究/` 回流入口。

## 6. 安全边界(全程不变)

- `raw/**` 只读不可变;ingest/apply 永不写入。
- 正式写入唯一入口仍是 `apply --write`;无 `--write` 一律 dry-run。
- 不自动压缩/删除正式 `wiki/**`;整固重写必须走 dry-run → 人审 → write。
- 稳定 CLI 入口 `npm run codex:ingest -- ...` 不变;新能力以新子命令/新 flag 加入,默认行为兼容。
- live 库(`/path/to/your-trading-wiki`)对本仓库只读;测试一律用最小 synthetic fixture。
